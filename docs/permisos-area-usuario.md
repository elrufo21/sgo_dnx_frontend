# Permisos por área y usuario

Configuración ofrece **Permisos por área** (`/configuration/permissions`) y **Permisos por usuario** (`/configuration/permissions-users`). El primero define el perfil base. El segundo muestra mediante casillas el acceso efectivo y permite asignar o quitar permisos individuales, también para usuarios administradores. Las excepciones tienen prioridad sobre el área. Un administrador sin excepción explícita conserva acceso por defecto; una denegación individual se aplica también en los controladores protegidos.

En permisos por área se selecciona directamente el área. En permisos por usuario se selecciona directamente un usuario activo de la compañía, identificado también por su área; la pantalla obtiene automáticamente esa área para cargar y guardar el perfil heredado, sin pedir una selección previa.

Ambas pantallas presentan los permisos existentes en una tabla con búsqueda por módulo, código, nombre o descripción. En usuario, cambiar una casilla guarda una excepción individual; las casillas que no se cambian conservan sus excepciones o herencia previas. Permitir todo modifica todos los permisos, incluso los ocultos por la búsqueda. No se agregan permisos separados de creación, edición o eliminación que no existan en el catálogo.

Los perfiles se guardan en `dbo.Indicador` y los resuelve `dbo.usp_PermisoIndicador`. **Heredar** elimina únicamente la excepción de ese permiso. Las excepciones siguen al usuario si cambia de área dentro de la misma compañía; el perfil de área se toma de la nueva área al iniciar sesión otra vez. Si existen varios perfiles históricos del mismo usuario en la compañía, se usa el de mayor ID: el responsable SQL debe revisar duplicados antes de aplicar el cambio.

Los permisos individuales ya guardados se conservan tal como están, incluso si coinciden con el perfil de área. Esto evita alterar accesos existentes, pero esos valores no heredarán cambios hasta que se elija **Heredar** explícitamente. La instalación no modifica los perfiles existentes.

La API usa `GET /Permisos/areas` y `GET /Permisos/usuarios` para listar áreas y usuarios activos de la compañía, `GET /Permisos/perfil` para cargar el perfil, `PUT /Permisos/perfil` para guardarlo y `GET /Permisos/mis-permisos` para los efectivos de sesión. Los perfiles solo pueden administrarse por administradores o usuarios con `CONFIGURACION.PERMISOS`. La pantalla bloquea el guardado si no puede cargar el perfil o el contrato actualizado.

Para desplegar, el responsable SQL debe respaldar y revisar `Indicador`, los usuarios administradores y el script [20261104_permisos_herencia.sql](../../sgo_dnx_backend/scripts/sql/20261104_permisos_herencia.sql), y aplicarlo en cada base correspondiente antes de publicar frontend y backend. No se ha ejecutado. El script requiere el catálogo y esquema existentes y no determina quién debe ser administrador.

El formulario de mantenimiento crea usuarios nuevos sin acceso de administrador y conserva el indicador existente al editar. No cambia usuarios existentes. Al recargar con una sesión activa, el frontend consulta `mis-permisos` para actualizar el menú; si cambia el área del personal, debe volver a iniciar sesión porque el área se incluye en el token. Para compatibilidad con una API anterior que responde administrador con lista vacía y no indica `gestionIndividual`, se conserva el acceso completo anterior; para restringir administradores debe estar instalada la API actualizada. El acceso alternativo Identity sin usuario del catálogo mantiene su comportamiento de administrador y no aparece en el selector. La API valida permisos en los controladores que tienen la protección correspondiente; la cobertura de todos los endpoints no está completa y debe revisarse antes de considerar estos perfiles como restricción integral de seguridad. Las claves de administrador para operaciones especiales son una verificación independiente.
